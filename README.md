# 競輪予想アプリ

個人利用の競輪予想PWA。ライン／脚質実力／データ統計の3本柱でスコアリングし、印（◎○▲△×）と買い目候補を提示する。

設計の詳細は以下を参照:

- [`01_競輪予想アプリ_仕様会議まとめ.md`](./01_競輪予想アプリ_仕様会議まとめ.md) — 仕様・設計書
- [`02_Claude_Code_開発プロンプト集.md`](./02_Claude_Code_開発プロンプト集.md) — Phase別の開発プロンプト集

## フォルダ構成

| フォルダ | 内容 |
|---|---|
| `app/` | Next.js App Router（画面・manifest） |

## データベース：Turso（libSQL）

外出先のiPhoneからも常時アクセスできるよう、DBはローカルファイルではなく
[Turso](https://turso.tech)（SQLite互換のクラウドDB、無料枠あり）を使う。
Next.js（`@libsql/client`）とPythonスクレイパー（`libsql-client`）の両方が
同じTursoデータベースを読み書きする。

### 1. Tursoデータベースを作成する

1. [turso.tech](https://turso.tech) でアカウント作成（GitHubログイン可）
2. ダッシュボードで新しいデータベースを作成
3. データベース詳細ページで以下を控える：
   - **Database URL**（`libsql://xxxx.turso.io`）
   - **Auth Token**（Create Tokenで発行）

### 2. ローカル環境変数の設定

```bash
cp .env.local.example .env.local
# .env.local を編集して TURSO_DATABASE_URL / TURSO_AUTH_TOKEN を埋める
```

### 3. スキーマ初期化

```bash
cd scraper
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt
playwright install chromium

cd ..
scraper\.venv\Scripts\python.exe db\init_db.py
```

**動作確認済み。**Python版`libsql-client`(0.3.1)は`libsql://`（WebSocket/Hrana）接続だと環境によってハンドシェイクに失敗することがあったため、`scraper/db.py`内で`https://`に自動変換して接続している（TypeScript側の`@libsql/client`は`libsql://`のままで問題ない）。また同クライアントのHTTPトランスポートは対話的トランザクション（BEGIN/COMMIT）に非対応のため、`keirin_scraper.py`の`save_to_db`は「race行の確定はRETURNING付きの単発execute、残りは1回のbatch()にまとめて送信」という方式にしている。

## デプロイ手順（Vercel + Turso + GitHub Actions）

### 1. GitHubリポジトリを作成してpush

```bash
gh auth login          # 初回のみ・ブラウザでの認証が必要
gh repo create keirin-prediction-app --private --source=. --remote=origin
git push -u origin master
```

### 2. GitHub Secretsを設定（Actionsでのスクレイパー実行用）

```bash
gh secret set TURSO_DATABASE_URL --body "libsql://xxxx.turso.io"
gh secret set TURSO_AUTH_TOKEN --body "xxxxxxxx"
```

以降、GitHubリポジトリの「Actions」タブから `Scrape keirin race data` ワークフローを手動実行（`workflow_dispatch`）すると、PCを起動していなくてもレースデータを取得できる。デフォルトではスケジュール実行は無効にしてある（`.github/workflows/scrape.yml` 内のcronはコメントアウト）。有効化する場合も、KEIRIN.JPへの節度あるアクセス（低頻度・個人利用の範囲）を必ず維持すること。

### 3. Vercelにデプロイ

```bash
npx vercel login       # 初回のみ・ブラウザでの認証が必要
npx vercel link
npx vercel env add TURSO_DATABASE_URL production
npx vercel env add TURSO_AUTH_TOKEN production
npx vercel --prod
```

またはVercelダッシュボードでGitHubリポジトリをImportし、Environment VariablesにTURSO_DATABASE_URL/TURSO_AUTH_TOKENを設定してデプロイしてもよい（以後はgit pushで自動デプロイされる）。

## データ取得（スクレイピング）

```bash
cd scraper
# 本日発売中の開催場一覧を確認
.venv\Scripts\python.exe keirin_scraper.py --list-venues

# 1レース分だけ取得してDBに保存
.venv\Scripts\python.exe keirin_scraper.py --venue-index 0 --race-no 1
```

**既知の制約・注意点：**

- KEIRIN.JPのrobots.txtは出走表・オッズ・結果ページを許可リストに含めていない。本プロジェクトは個人利用として非準拠で実装している（[01_競輪予想アプリ_仕様会議まとめ.md](./01_競輪予想アプリ_仕様会議まとめ.md)の注意点も参照）。アクセス頻度は絶対に上げないこと。
- サイトはJSFベースのステートフルな作りで、`data-encp` という暗号化パラメータとセッションに強く依存する。サイト側のUIボタンをクリックしてサイト自身にAJAX（`/pc/json?type=...`）を発行させ、その応答を横取りする方式で実装している（`keirin_scraper.py` の `JsonCapture`）。サイト構造が変わると壊れやすい。
- 現状オッズは3連単のみ対応（`JST011` の `kake` パラメータを変えれば他の券種にも拡張可能）。
- ライン情報（隊列構成・番手位置）は`narabiyoso`（並び予想）から取得済み。ただしレース確定前の一定期間しか提供されないことがある（`ryoikiFlg`が`false`の場合は未提供）。
- 複数日開催の場合、開催場ページはデフォルトで初日を表示するため、本日の日付タブに自動で切り替える処理を入れている（`_switch_to_today`）。単日開催では何もしない。
- バンク特性（周長・直線長・カント・決まり手傾向）は `/pc/jyoguide`（robots.txt許可ページ）から取得し `bank_info` テーブルに保存。開催場単位でほぼ不変なため30日キャッシュ。
- 選手の出走間隔・過去の同条件成績は `/pc/racerprofile`（robots.txt許可ページ）の「最近の成績」から `racer_race_history` テーブルに保存。日付はMM/DDのみで年を厳密に特定していない簡易実装。選手単位で1日キャッシュ。
- 天候は `races.tenki`/`races.husoku` に保存されるが、**レース終了後の実績値のみ**取得可能（事前予報ではない）。そのためスコアリングには反映していない（過去レースの振り返り分析用）。
- ギア倍数は未取得（選手プロフィールページ側でのさらなる補完が必要）。

## 過去レースの取得（バックテスト用・WINTICKET）

KEIRIN.JPは「本日/明日」のライブ発売中レースしか出走表・結果を取得できる入口がなく、
過去日程はカレンダー表示のみでクリック不可（過去レースのバックテストが作れない）。
そのため過去データの取得だけは公式ネット投票サイト WINTICKET を使う
（`scraper/winticket_scraper.py`）。こちらはPlaywright不要、素のHTTP GET + BeautifulSoup
でSSRされたHTMLから直接パースできる。

```bash
cd scraper
.venv\Scripts\python.exe winticket_scraper.py --venue iwakidaira --days-back 7
```

- 出走表: `https://winticket.jp/keirin/{venue}/racecard/{cupId}/{day}/{raceNo}`
- 結果: `https://winticket.jp/keirin/{venue}/raceresult/{cupId}/{day}/{raceNo}`
- 開催日程一覧: `https://winticket.jp/keirin/{venue}/schedule/{YYYYMM}`（`cupId`＝開催初日8桁+開催場コード2桁を列挙）
- 各cupIdについて day=1.. / raceNo=1.. を404が返るまで反復して開催全体を走査する。
- 選手の識別キー（`racers.snum`）はKEIRIN.JP側の選手登録番号と体系が異なる可能性があるため、
  衝突を避けて `"wt" + WINTICKETのcyclist ID`を使う（KEIRIN.JP由来のレコードとは別選手として扱われる）。
- DB保存は`keirin_scraper.py`の`RaceData`/`save_to_db`をそのまま流用（スキーマはデータ取得元に依存しない）。
- 節度あるアクセス間隔（デフォルト1.5秒/回）を必ず空けること。全国全開催場の長期間取得は
  数千リクエスト規模になるため、対象開催場・期間を絞って段階的に実行すること。

### 選手プロフィールの補完（前期級班・直近成績）

出走表ページ単独では前期級班（昇降級判定用）と選手ごとの出走履歴（出走間隔・同開催場
成績用）が取得できない。選手プロフィールページ（`/keirin/cyclist/{id}`）には
「級班履歴」（前期分も含む）と「直近20レース成績」（開催日・開催場略称・その開催内の
各レース着順）があるため、`scrape_one_race`実行時に選手単位で自動補完する
（`enrich_entries_with_history`、選手ごとに鮮度をキャッシュするため節度あるアクセスに配慮）。

既存レースの選手をまとめて補完する場合:

```bash
cd scraper
.venv\Scripts\python.exe backfill_racer_profiles.py
```

2026年8月時点で2001選手（新規レース取得時に自動取得される分は対象外）を約50分で
補完した。この結果、出走間隔・同開催場成績・昇降級のいずれもデータが常にニュートラル値
だった状態から実データで動くようになり、バックテストで◎的中率42.7%→45.5%・
全シナリオ合成回収率70.7%→81.4%と大きく改善した（下記「予想ロジックの検証」参照）。

### バックテスト集計（的中率・回収率）

```bash
npx tsx scripts/backtest.ts        # 結果が確定している全レース
npx tsx scripts/backtest.ts 13,63  # 開催場コードで絞り込み（例: いわき平・防府）
```

結果(`results`)が確定している全レースに対して現在のスコアリング・シナリオ生成ロジックで
`predictRace()`を再実行し（`predictions`テーブルにもスナップショットを保存するため`/history`
画面にも反映される）、実際の着順と照合してシナリオ別・3連複ボックスの的中率と回収率を出力する。
回収率はWINTICKET結果ページの確定払戻金から算出（3連単のみ。3連複の払戻は未取得）。

### 予想ロジックの検証・再調整用スクリプト

```bash
npx tsx scripts/diagnose-ranking.ts     # 総合スコア順位と実際の1着の関係、脚質・隊列位置・決まり手の分布
npx tsx scripts/diagnose-truerates.ts   # 隊列内位置・ライン人数・脚質ごとの「真の勝率」（母数で正規化）
npx tsx scripts/diagnose-linefinish.ts  # 上位3着の隊列位置の組み合わせ（同ライン決着か、番手差しか等）
npx tsx scripts/diagnose-venue.ts       # 開催場別の決まり手割合・グレード別の隊列内位置勝率
npx tsx scripts/diagnose-classchange.ts # 昇級/降級/変動なし別の勝率・複勝率
npx tsx scripts/diagnose-interval.ts    # 出走間隔バケット別の勝率
npx tsx scripts/diagnose-banklength.ts  # 周長（333/400/500m）別の決まり手割合・隊列内位置勝率
npx tsx scripts/diagnose-confidence.ts  # 本命と2位のスコア差別の◎的中率、選手ごとの◎採用回数分布
```

スコアリングの重みを勘や一般論だけで調整すると、見かけ上もっともらしくても実際には
改善しない（むしろ悪化する）ことがある。例：2026年8月時点で43開催場・約1000レースの
バックテストで「実際の1着の65%がライン先頭だった」ことが分かったため、隊列位置の
配点を先頭優遇に変更したところ、単体では◎的中率がわずかに改善したが、脚質評価側
（`calculateKyakushitsuScore`の`fitScore`、逃×先頭を優遇）と同時に適用すると
情報が重複してかえって◎的中率・回収率とも悪化した（先頭に立つ選手はもともと
「逃」脚質であることが多く、両方に同じ強さの根拠を二重に加点してしまうため）。
最終的には脚質側の調整のみを残し、ライン側の隊列位置配点は据え置いている
（`lib/scoring.ts`の`calculateLineScore`のコメント参照）。

もう一例：`diagnose-linefinish.ts`で「1着が番手だった時、2着は同ラインの先頭
（自分の前を走っていた選手がそのまま粘る）」が53.2%と最多だと分かったため、
まくり/差し一撃シナリオの2・3着候補プールを「差された側（本命ライン）優先」から
「軸自身のライン優先」に変更したところ、まくり/差し一撃の的中率が5.2%→6.2%、
全シナリオ合成の的中率が29.7%→30.6%に改善した。

3例目：`diagnose-venue.ts`で開催場ごとの決まり手割合が実際には大きくばらつく
（例：防府は逃57%、いわき平は差54%）と分かった一方、`bank_info`テーブルは
43開催場中2件しか登録されておらずほとんどの開催場でこの情報が使われていなかった。
そこで`getVenueKimariteRates`（`lib/repository.ts`）を追加し、自前のresults実績
から開催場別の決まり手割合を直接算出してバンク適性評価に使うようにした。
ただし母数条件（`minRaces`）を緩く（15件）設定すると、母数20〜30件程度の開催場の
推定値がノイズで振れすぎてかえって◎的中率・回収率とも悪化した。40件まで上げると
小規模開催場は素通し（ニュートラル値）になる一方、対象になった開催場では改善した
ため、40を採用している（`getVenueKimariteRates`のコメント参照）。

なお`diagnose-venue.ts`ではグレード別（F1/F2/G3）の隊列内位置勝率も出せるが、
G3のみ「番手(16.1%)が先頭(13.8%)を上回る」という一見興味深い逆転が見えたものの、
G3のサンプル数（117レース）では標準誤差(≈2.8pt)が観測差(2.3pt)より大きく、
統計的に有意とは言えないと判断し、グレード条件分岐は見送っている。

4例目：選手プロフィールの補完（前期級班・直近成績）後、`diagnose-classchange.ts`で
昇級/降級/変動なし別の勝率を確認したところ、降級12.9%・昇級13.7%とほぼ同水準だった
（7174出走の大きなサンプル）。`calculateKyakushitsuScore`は「降級直後は新しい級で
相対的に格上」「昇級直後は格上の相手と苦戦」という定石で+15/-10点調整していたが、
この根拠が実績で確認できなかった。実際に調整を外してバックテストすると◎的中率
42.7%→45.5%・複勝率72.3%→73.8%・3連複ボックス的中率35.5%→36.1%と改善したため、
調整を無効化した（`lib/scoring.ts`の`calculateKyakushitsuScore`のコメント参照。
昇降級の判定・表示自体は参考情報として残している）。

5例目：`diagnose-interval.ts`で出走間隔バケット別の勝率も確認したが、全出走の99%が
「0-2日(連闘)」バケットに集中しており評価不能だった。原因は、複数日開催（3〜4日制）の
2日目以降のレースでは「直近の出走」が同じ開催の前日になり、これが定石でいう
「連闘」（別開催での連続出走による疲労）とは意味が異なるため。現状のデータ収集が
特定期間に集中しているための偏りで、季節をまたいだ疎らなデータが貯まれば
再検証できる見込み（`calculateIntervalScore`の閾値は変更していない）。

6例目：`diagnose-banklength.ts`で周長（333m/400m/500m。races.kyori/shukaiの
1周あたり距離から推定）別の決まり手割合を確認したところ、333mは400mより差し決着の
比率が低い（36.1% vs 43.9%）という違いが見つかった（隊列内位置の勝率は周長による
差がほぼ無かった）。43開催場中15開催場ほどが`getVenueKimariteRates`の母数条件
（40レース）に届いていなかったため、`getVenueKimariteRatesWithFallback`で
「開催場単体→同じ周長の開催場をまとめた値（母数100件以上）→ニュートラル」の
3段階フォールバックを追加した。ただしバックテストでは的中率・回収率とも
ほぼ変化なし（誤差1ヒット未満）で、明確な改善効果は確認できていない。
今回の対象データでこのフォールバックが実際に使われた開催場・レース数が
少なかったためと見られる。信号自体（周長による決まり手傾向の違い）は実在するため
実害はないと判断してコードは残しているが、「改善した」とは言えない状態である。

なお選手個人のバンク相性（例：「333mバンクが得意な選手」）も検討したが、
2種類以上の周長でそれぞれ3走以上の実績がある選手は2002人中227人（11%）に
留まり、大半の選手はどのみちニュートラル評価になってしまうため、現状のデータ量では
実装を見送っている。データが増えて対象選手の割合が上がれば再検討する。

### おすすめレース：本命と2位のスコア差による「高信頼度」バッジ

`scripts/diagnose-confidence.ts`で本命(1位)と2位の総合スコア差ごとに◎の実際の
的中率を確認したところ、差が10点未満だと単勝的中率37〜46%だったのに対し、
10〜20点差では81.7%（104レース）、20点差以上では100%（8レース）と大きく
跳ね上がることが分かった。この結果を受けて、レース一覧画面（`/`）の本日開催中
レースに、本命と2位のスコア差が10点以上のレースへ「高信頼度」バッジを表示する
ようにした（`app/page.tsx`の`HIGH_CONFIDENCE_MARGIN`）。過去レース分は毎回
予想し直すコストが大きいため対象外にしている。

一方、「◎に選んだ選手の実際の的中率が高い選手」をバッジ表示する案（おすすめ選手）
も検討したが、同じスクリプトで確認したところ◎に選ばれた回数の最大は6回、
5回以上選ばれた選手は2002人中14人しかおらず、8回以上は0人だった。個々の選手の
的中率を統計的に信頼できる母数がまだ無いため、実装を見送っている。

### 買い目の絞り方：本命と対抗のスコア差に応じた調整

「高信頼度」の判定基準（本命と対抗のスコア差）を使って、本命シナリオの買い目自体も
調整するようにした（`lib/scoring.ts`の`generateScenarios`）。

- スコア差が`HIGH_CONFIDENCE_MARGIN`(10点)以上：単勝的中率が高い実績があるため、
  本命の3連単を最小構成（2点）まで絞る。買い目提案画面には単勝での勝負を促す
  「単勝おすすめ」カードも表示する（`predictRace`の`winSuggestion`）
- スコア差が`LOW_MARGIN_THRESHOLD`(5点)未満：本命と対抗の力が拮抗しているとみて、
  1着・2着を入れ替え可能なボックス買い（例: 1=2-3）にする（`formationBoxTop2`）

**この検証で判明した重要な注意点**：1023レース規模のバックテストをTurso（HTTP経由）に
対して実行すると、まれに`502 SERVER_ERROR`が発生することがある
（1レースあたり数十クエリ×1000件超で連続アクセスするため）。最初の検証時にこれが
原因で不完全な集計から「回収率102.3%→105.5%に改善」という誤った数値を得てしまい、
同じコードで再実行したところ回収率96.2%（ほぼ横ばい〜微改善）という異なる結果になった。
必ず**同じ条件で2回以上実行し、数値が再現することを確認してから判断すること**。
再発防止のため`lib/db.ts`の`getDb()`に一時的なエラー（502等）への自動リトライを追加した。

最終的に再現確認した数値（本命単体の買い目のみ絞る前後比較）：
[本命+単騎一撃]の回収率95.4%（絞りなし）→96.2%（絞りあり）、本命単体は
的中率21.0%→20.2%・回収率88.1%→89.0%と、的中率をわずかに犠牲に回収率が
わずかに改善する、ねらい通りだが小さな効果だった。

### 回収率の検証：シナリオの組み合わせ別ROI

`scripts/backtest.ts`実行時に「シナリオの組み合わせ別 回収率ランキング」も出力される
（4パターンの全部分集合＝15通りを賭け金・払戻の合算で比較）。2026年8月時点の1023
レースでは、全シナリオ合成（4パターン全部に賭けた場合）の回収率70.7%に対し、
「本命＋単騎一撃」の2つだけに絞ると204ヒットという十分なサンプルで回収率96.5%まで
上がった。逃げ粘り込み・まくり/差し一撃は単体でも他との組み合わせでも一貫して
回収率を下げていた。

この結果を受けて、`scenario_stats`テーブル（`db/schema.sql`）を追加し、
`scripts/backtest.ts`が実行のたびにシナリオ別の的中率・回収率実績をUPSERTする
ようにした。買い目提案画面（`/races/[id]/bets`）は`getScenarioStats()`で
このキャッシュを読み、各シナリオカードに実績（的中率・回収率・母数）を表示する
（回収率100%以上は緑字で強調）。展開パターン自体は4つとも維持し、どれに賭けるかは
実績を見ながらユーザーが判断できるようにしている（シナリオを削るのではなく、
情報を追加する形にした）。

`scenario_stats`はキャッシュなので、データが増えたら`scripts/backtest.ts`を
再実行して更新すること（自動更新の仕組みはまだ無い）。

### レース展開予想：どのシナリオがこのレースで有力か（likelyRank）

上記の実績（`scenario_stats`）はシナリオ全体の平均であり、「このレースでは
本命ではなく逃げ粘り込みの方が有力」といった1レース単位の判定はできていなかった。
そこで`generateScenarios`（`lib/scoring.ts`）に`likelyRank`を追加した。
各シナリオの軸選手の総合スコアをレース内で比較し、1位（＝本命の軸。定義上必ず
最高スコアなので自明に1位）から順位付けする。逃げ粘り込み・まくり/差し一撃・
単騎一撃の軸スコアが本命にどれだけ肉薄しているかで、「本命が抜けているレース」か
「拮抗していて他の決着もありうるレース」かを相対的に判定する。

`scripts/validate-likelyrank.ts`でこの順位付けに実際の予測力があるか検証した
（1023レース）。3シナリオとも、レース内順位が高い（＝本命に近い）ほど実際の
的中率も明確に高かった：

| シナリオ | rank2的中率 | rank3的中率 | rank4的中率 |
|---|---|---|---|
| 逃げ粘り込み | 7.1% | 4.2% | - |
| まくり/差し一撃 | 8.1% | 3.0% | 0.0% |
| 単騎一撃 | - | 3.6% | 1.6% |

単調に的中率が下がっており、単なる順位付けでも意味のある情報になっていることを
確認できたため採用した。買い目提案画面では、レース内2位のシナリオに
「このレースでは本命に次ぐ有力な展開」、3位以下に「このレースでは可能性低め」の
バッジを表示する（本命は自明に1位のためバッジなし）。

**重みを調整する際は必ずこれらの診断スクリプトと`scripts/backtest.ts`で
「変更前後」を比較してから採用すること。**

### 展開予想の深掘り：周回ごとの連続的な走行位置データは無し、選手個人の決まり手回数・S/H/Bカウントはあり

「ホーム・バックの位置取りから最終周回の隊列を予想する」という案を検討した。
WINTICKET・KEIRIN.JPどちらにも周回ごとの走行位置データ（ラップタイムや
順位推移）は存在しないことを確認した（結果ページは最終着順と決まり手のみ。
「レース後コメント」相当のインタビューAPIも前日コンディションの質疑応答で
レース展開とは無関係）。連続的な周回追跡という意味では実装不可能。

※後日、出走表に離散的な位置指標（S/H/B、下記）があることが判明し、この節の
タイトルはその訂正を反映している。詳細は本節末尾の追記を参照。

代わりに、出走表ページに選手ごとの「1着・2着に入った際の勝ち方の回数」
（逃げ/捲り/差し/マークの内訳。WINTICKET公式ヘルプで意味を確認済み）があることが
分かったため取得するようにした：

- `db/schema.sql`: `racers`テーブルに`kimarite_nige_count`等4列を追加
- `scraper/winticket_scraper.py`: 出走表の該当列をパースして保存
- `lib/scoring.ts`: `calculatePersonalMoveFitScore`で、選手の脚質に対応する
  決まり手（例: 脚質が「逃」なら逃げ）で実際に何割上位（1-2着）に来ているかを算出

このバックフィルのため全43開催場を再スクレイプ（1122レース、選手2038人中2019人＝
99%で決まり手回数を取得）した。この過程でTursoへの大量連続アクセスにより
Python側スクレイパーでも502エラーが複数回発生したため、`scraper/db.py`にも
（TypeScript側`lib/db.ts`と同様の）自動リトライを追加し、選手の鮮度チェックも
2クエリから1クエリに統合してTursoへのアクセス回数を削減した。

**この選手個人の決まり手適性をデータ統計スコアに重み0.1・0.2で組み込んで
バックテスト検証したが、重みを上げるほど◎的中率が単調に悪化した**
（1086レースで重み0:42.3%→0.1:41.7%→0.2:40.5%）。回収率側で改善して見えた
部分（まくり/差し一撃が66.9%→88.8%等）も、的中件数（母数42件）自体は
変わらずROIだけ変動していたため、少数サンプルの分散によるものと判断した。
総合スコアへの単純な重み付け合成では効果が無かったため無効化（重み0）した。
取得したデータ自体は残しており、まくり/差し一撃・逃げ粘り込みシナリオの
軸候補選定など、より限定的な使い方であれば将来再検証の余地がある
（`lib/scoring.ts`の`calculateStatsScore`のコメント参照）。

#### 追記：S/H/B（出走表の位置系カウント）は信号としては強いが、合成では効果なし

決まり手回数の検証後、ユーザーから「出走表にあったS/H/B列は使えないか」と
指摘を受けた。このS/H/B列はセッション序盤に一度目にしていたが意味を調べずに
放置しており、まさに聞かれていた「ホーム/バック位置」に直結するデータを
見落としていたという反省点だった。WINTICKET公式ヘルプ（`/support/beginner`）で
定義を確認：
- **S（Standing）**：スタートの号砲後、先頭誘導員の後方に速やかに付けた回数（好スタート回数）
- **H（Home）**：最終周回のホーム線（ゴール線でもある）を先頭通過した回数
- **B（Back）**：最終周回のバックストレッチ線を先頭通過した回数。WINTICKET側の
  説明文で「ここでの位置がゴールでの着順に大きく影響することが多い」と明言されている

`db/schema.sql`に`standing_count`/`home_lead_count`/`back_lead_count`を追加し、
`scraper/winticket_scraper.py`で取得、全43開催場を再スクレイプして
バックフィルした（1159レース、選手2087人中2034人＝97%でS/H/B取得）。

**診断（`scripts/diagnose-shb.ts`、7994出走・結果確定分）で信号自体は非常に強かった：**
レース内でのB（back_lead_count）順位別の真の勝率が
1位27.0%→2位20.7%→3位16.7%→4位14.2%→5位8.0%→6位6.7%→7位5.8%と
極めて綺麗な単調減少。生カウントのバケット別勝率も8.8%→14.1%→21.3%→23.3%→27.0%と
単調増加しており、WINTICKET自身の「着順に大きく影響する」という説明と一致した。
Hも近い傾向、Sは弱くノイジーだったためBのみを採用することにした。

この強い信号を根拠に`calculateLeadPositionScore`（レース内でのB順位を
実測勝率テーブルに変換するスコア）を実装し、データ統計スコアに
`LEAD_POSITION_WEIGHT`で重み付け合成してバックテストで検証した。
**しかし、決まり手回数のときと同じ結果になった**（1148レース、
重み0:42.0%(482)→0.1:41.9%(481)→0.2:41.7%(479)。0.2は2回実行し完全再現）。
◎的中率は重みを上げるほど単調に悪化した。単独の信号としては強いのに合成では
効果が無い（むしろ悪化する）理由は、Bで先頭に立つ選手は結局
heikin_tokuten/rentairitu2など既存の統計評価が既に高評価している選手と
重なりが大きく、追加の重みは新しい情報を足すのではなく既にチューニング済みの
他要素の重みを薄めるだけになったためと考えられる。このため
`LEAD_POSITION_WEIGHT`は0（無効化）としている。データ自体
（`standing_count`/`home_lead_count`/`back_lead_count`）は選手の実データとして
保持しており、決まり手回数と同様、より限定的な使い方（シナリオ軸候補選定等）
であれば将来再検証の余地がある。

## 予想ロジック（スコアリング）

```bash
npm run score <race_id>   # 例: npm run score 1
```

Tursoに保存されている `races.id` を指定すると、①ライン ②脚質実力 ③データ統計 の3スコアと
総合スコア・印（◎○▲△×）・3連単フォーメーション/3連複ボックス候補を表示する。
重みは `settings` テーブル（`score_weight_line` 等）で調整可能（`/settings` 画面から編集可能）。

**展開パターン別の複数予想（`generateScenarios`）：** 総合スコア1位を機械的に軸にするだけでなく、レース展開が複数ありうることを踏まえて2〜4パターンの軸候補を出す。
- **本命**：総合スコア1位がそのまま押し切る想定
- **逃げ粘り込み**：ライン先頭の選手が番手・3番手に守られて単独で粘り切る想定
- **まくり/差し一撃**：先頭以外の位置で脚質が追・両（追い込み適性）の選手が外から差す想定。バンクの捲り決まり手率（`bank_info.makuri_pct`）が高いほど根拠として言及される
- **単騎一撃**：ライン人数1（単騎）の選手が対象。単騎は隊列構成上ライン評価が低く出やすいが、個人の実力（脚質実力・データ統計スコア）が高ければ距離や出走間隔に関わらず単独で上位に飛び込むことがあるため、ライン評価を除いた個人力が最も高い単騎選手を軸にする

各パターンで軸を変え、それぞれ「1頭軸流し」形式のフォーメーションを生成する。2着・3着候補は総合スコア順ではなく、パターンごとの優先ライン（本命／逃げ粘り込みは軸と同じライン、まくり/差し一撃は差される側＝本命ラインのメンバー、単騎一撃は優先ラインなし＝総合スコア順）を先頭に並べた専用プールから選ぶ（`buildLineAwarePool`）。点数は各パターンの予算（20点をパターン数で均等割り）内でM×(M-1)が収まる最大のMを自動選択し（`formationFromPool`）、全パターン合計が3連単20点の上限を超えないようにする。同じ選手が複数パターンの軸に重複する場合は後続パターンをスキップし、実質的に異なる決着筋だけを出す。3連複ボックスは展開パターンに依らない上位4車の総当たり（保険的な買い方）として別枠で1つだけ表示する。

**データ統計スコアの内訳（重み内訳）：**
- バンク適性(20%)／出走間隔(15%)／過去の同開催場成績(20%)／位置別勝率(20%)／連対率(25%)
- **オッズは意図的に不使用**（群衆の人気度を自分の予想スコアに混ぜると群衆と同じ判断に収束してしまうため）。オッズ自体はDBに保存されるが、スコアリングでは参照しない。
- 天候は事前予報が存在しないため対象外（`races.tenki`にレース終了後の実績値のみ保存、振り返り分析用）

**位置別勝率：** 公式サイトに統計が存在しないため、自前で蓄積した `entries.line_position` × `results.finish_pos` から算出する（`getPositionWinRates()`）。母数が少ないうちは選手自身の通算勝率を事前分布としたベイズ縮小推定で極端な値を抑えている（`calculatePositionWinRateScore`）。スクレイピング件数が増えるほど精度が上がる。

**昇級・降級（脚質実力スコアに反映）：**
- 競輪の級班替えは毎年1月・7月。`racers.prev_class_rank`（前期級班）と`class_rank`（今期級班）を比較し昇級/降級を判定する。
- 切り替え1ヶ月目（1月・7月）は全量、2ヶ月目（2月・8月）は半量で、降級選手（新しい級では相対的に格上）に加点、昇級選手（格上の相手と走る）に減点する調整を入れる。3ヶ月目以降は調整なし（`classChangeAdjustmentFactor`）。

**その他の制約：**
- ギア倍数は未取得のため脚質実力スコアには含めていない。
- オッズは1回分のスナップショットのみのため「オッズの動き（推移）」は未反映。
- 過去の同条件成績は開催場名の1文字一致による近似マッチング（`venue_abbr`が略称のため）。

## 精度検証機能（Phase 4）

出走表画面の「この予想を記録する」ボタンで、その時点のスコア・印を `predictions` テーブルにスナップショット保存する（発走前に記録する想定）。レース結果（`results`）が揃うと、履歴画面で以下を自動集計する：

- ◎の単勝的中率／複勝的中率（3着以内）
- 3連単フォーメーションの的中率
- 回収率（フォーメーション各点に100円均等買いした場合の参考値。的中点のオッズは予想記録時点のスナップショットを使うため、公式の確定払戻金とは異なる場合がある）

`predictions`にスナップショットを残すのは、`racer_race_history`や`results`など元データが後から更新され続けるため、「予想した時点のスコア」を固定して振り返れるようにするため。
